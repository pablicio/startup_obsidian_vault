# 🔁 Revisão: Produto é hipótese antes de ser solução

## 📝 Conteúdo para revisar

Antes de ser uma solução para o usuário, qualquer produto é uma **hipótese** da equipe. Tratar como solução prematuramente é o erro que mata a maioria das startups — não falta de execução, mas excesso de certeza.

O ciclo Build-Measure-Learn formaliza isso: construir o menor experimento (MVP) → medir o que indica se a hipótese é verdadeira → aprender se deve perseverar ou pivotar.

Consequência contraintuitiva: **invalidar rápido uma hipótese é valioso**. Uma startup que descobre em 2 semanas que estava errada e pivota está em posição melhor do que uma que executa a hipótese errada por 6 meses com perfeição.

**P1:** Qual é a diferença prática entre tratar o produto como "solução" vs tratá-lo como "hipótese"?

**P2:** O que é o ciclo Build-Measure-Learn? Descreva cada etapa em uma frase.

**P3:** Por que invalidar uma hipótese rapidamente é melhor do que executar lentamente a hipótese certa?

---

## ✅ Respostas

**R1:** Tratar como solução → o objetivo é entregar, o sucesso é o lançamento, a pergunta é "estamos construindo certo?". Tratar como hipótese → o objetivo é aprender, o sucesso é a validação, a pergunta é "estamos construindo a coisa certa?".

**R2:** Build: construir o menor experimento que testa a hipótese central. Measure: medir o que indica diretamente se a hipótese é verdadeira. Learn: decidir com base na evidência — perseverar ou pivotar.

**R3:** Porque o recurso mais escasso em startup é tempo. Cada semana em uma hipótese errada é uma semana que poderia ter sido usada para testar a hipótese certa. Velocidade de invalidação é velocidade de aprendizagem.
